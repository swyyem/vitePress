10 分钟面试自我介绍（双项目版·扩充版） ​

开场（约 1.5 分钟） ​

面试官好，我是 XXX，3 年多专注于前端架构与复杂业务系统方向的前端工程师。

我最近的工作主要围绕两个核心项目展开：

第一个是面向三甲医院的门诊医生临床诊疗平台——这是一个日活过千的核心业务系统，基于 qiankun 微前端架构，集成了 46 个业务子模块，覆盖了从挂号接诊、病历书写、医嘱开立、处方流转到检验检查全流程。它的技术复杂度在于：多个异构子系统需要实时联动，对数据一致性和稳定性要求极高——毕竟医疗场景容不得半点差错。

第二个是我主导从 0 到 1 搭建的企业级 Pro 组件库——基于 Vue 3 + TypeScript + Element Plus。它的诞生背景是：我们的多个中后台业务系统普遍面临三个高频痛点——大数据量表格渲染卡顿、动态表单配置繁琐、复杂选择器交互缺失。我从架构设计、核心组件研发到工程化体系搭建全程主导，目前这套组件库在公司多个业务系统中广泛复用，服务了十几位前端同事的日常开发。

两个项目一个偏复杂业务架构，一个偏底层能力抽象，让我在「大型系统治理」和「高复用基建设计」两个维度都有了深度实践。

接下来我从技术难点角度展开讲讲。

项目一：医疗诊疗平台（约 5 分钟） ​

难点 1：微前端架构治理与跨应用通信（约 2 分钟） ​

场景： 医院的信息系统不是一个单体应用，而是由很多子系统组成的——收费系统、药房系统、LIS 检验系统、PACS 影像系统等等。这些系统各自独立开发、独立部署，但在医生日常工作中它们需要紧密联动。

举个具体例子：医生在医生站给患者开了一个处方，药房系统要实时知道有新处方进来准备配药；检验科出了一个危急值结果，医生站要即时弹窗提醒医生处理——这种跨系统的实时联动是整个平台最核心的技术挑战。

技术难点： qiankun 作为微前端框架，它本身只负责子应用的加载、隔离和生命周期管理，并不提供应用之间的通信能力。而医疗场景对数据一致性要求极高——处方不能漏发给药房、危急值不能丢失、库存预扣减不能重复触发。

我的方案是设计了一个分层通信架构：

第一层是 props 透传，用于强绑定的确定性数据，比如当前患者上下文、用户身份。主应用切换患者时通过 props 变更，子应用自动感知并刷新——这是最简单但最可靠的方式。

第二层是全局自定义事件总线，用于松耦合的跨域事件。比如处方状态变更、库存预扣减这类需要多个系统联动的操作。我基于发布/订阅模式实现，但加入了三个关键机制：消息序列号用于排序、幂等处理防止重复消费、ACK确认保证消息被正确处理。

第三层是 WebSocket 实时推送，用于服务端驱动的不可预测时机的事件。比如检验结果是实验室什么时候出就什么时候推，我们控制不了时机。这里做了心跳保活、指数退避断线重连、以及最关键的——消息补偿队列，确保断线期间的消息不会丢失。

举个实际的场景： 处方开具后的库存预扣减。我采用的是乐观锁 + 前端异常回滚机制——医生点击开方后，前端先发预扣减请求，界面立即显示成功。但如果 3 秒内未收到服务端确认，会自动回滚并弹窗提示医生「库存不足」或「请重试」。这样既保证了用户体验的流畅性，又确保了数据一致性。

难点 2：高频诊疗工作台的性能优化（约 1.5 分钟） ​

场景： 医生的接诊页面是一个超级重页面——上面是患者基本信息和历史病历列表，中间是结构化病历编辑器（本质上是一个定制化的富文本），下面是医嘱录入区（动态表格，支持药品搜索、剂量联动等复杂交互），右边还有检验检查结果的时间轴展示。整个页面组件实例超过 300 个，表单字段 50 多个。

核心痛点有两个： 一是首屏白屏 3 秒以上，医生每天要接诊几十上百个患者，3秒的白屏体验是无法接受的。二是切换患者时整个页面全量重新渲染导致明显卡顿。

我做了五个层面的优化：

渲染层，把 46 个模块改为按区域懒加载——上半屏立即渲染，下半屏用 IntersectionObserver 进入视口才加载，加载期间展示骨架屏。

数据层，患者切换时不是销毁重建，而是做数据 diff 对比，只更新真正发生变化的模块。比如两个患者都是内科，诊断模板区域其实不需要重新渲染。

交互层，医嘱录入表格中用了虚拟滚动——一个慢病患者可能有 20-30 条长期医嘱，加上临时医嘱，DOM 数量从 500+ 降到始终只有 30 个左右。

输入层，药品搜索做 300ms 防抖加上 AbortController 竞态取消——医生输入「阿莫」时，「阿」字的请求如果还没返回就直接取消，只保留最后一次有效请求。

缓存层，常用药品字典、诊断模板这些变化频率很低的大数据，做了 IndexedDB 本地缓存，设置 24 小时过期，减少重复网络请求。

最终成果： FCP 从 2.8s 降到 1.2s，LCP 从 4.1s 降到 2.2s，切换患者从 1.2 秒优化到 300 毫秒以内。医生的反馈是「明显快了」。

难点 3：Webpack → Rsbuild 迁移与模块联邦（约 1.5 分钟） ​

背景： 微前端场景下有一个很大的问题——每个子应用都各自打包了一份 Vue、Element Plus、Pinia，46 个子模块意味着这些基础库被打包了 46 份。结果就是：开发时冷启动 40 秒以上，HMR 热更新要 2-3 秒，CI 打包一次要 4 分钟。

我的迁移方案分三步走：

第一步是构建工具替换，从 Webpack 迁移到 Rsbuild。Rsbuild 底层是 Rspack——用 Rust 重写的打包器，编译速度比 Webpack 快一个数量级。

第二步引入模块联邦，Vue 3、Element Plus、Pinia、Vue Router 这些基础库由主应用统一打包并暴露，子应用运行时从主应用获取，不再重复打包。这一步把子应用的产物从平均 1.2MB 降到了 300KB。

第三步是代码分割优化，按路由 + 按业务模块拆 chunk，配合 prefetch 策略预加载医生高频使用的模块。

迁移中遇到的坑：

最头疼的是模块联邦的版本一致性问题——主应用升级了 Element Plus 的小版本，几个子应用的样式就错乱了。最后的解决方案是 singleton: true 强制单例 + 严格的版本锁定策略 + CI 流水线加入版本一致性检查，不一致直接阻断合并。

另一个坑是 qiankun 的 JS 沙箱会劫持 window.__webpack_public_path__，和模块联邦的全局变量产生冲突。解决方案是把 publicPath 改为运行时动态注入，而不是构建时硬编码。

最终成果： 冷启动 40 秒缩短到 15 秒（降低 60%），HMR 从 2-3 秒变为毫秒级响应，CI 打包从 4 分钟降到 1.5 分钟。开发体验有了质的提升。

项目二：Pro 组件库（约 4 分钟） ​

难点 4：虚拟滚动 Hook 与 ProSelect 复杂交互（约 2 分钟） ​

场景： 业务中经常出现上万条数据一次性加载的场景。比如医院的药品字典有几万条，科室人员列表有上千条，这些都需要在下拉框或表格中流畅展示。直接渲染会产生大量 DOM，页面直接卡死。

我自研了一个虚拟滚动 Hook，核心思路是：

只渲染用户当前能看到的 20~30 个 DOM 节点，上方和下方用 padding 占位来模拟完整列表的高度，让滚动条的长度和行为与真实长列表一致。

四个关键技术细节：

第一是滚动监听的性能——我用 requestAnimationFrame 做节流，保证计算频率与屏幕刷新率同步，不会出现过度计算也不会出现延迟。

第二是动态行高的处理——这是虚拟滚动中最难的部分。我维护一个行高缓存数组，对已渲染的行用 ResizeObserver 实时测量真实高度写入缓存；未渲染的行用预估高度兜底。用户快速滚动到中间位置时，先用预估高度定位，渲染后再做一次微调修正。

第三是缓冲区机制——上下各多渲染 5 行，避免快速滚动时出现白屏闪烁。

第四是针对 ProSelect 场景特有的——虚拟滚动与键盘导航的配合。用户按方向键时，如果目标选项不在当前可视区域内，需要自动触发滚动把它滚到可见位置。

在此基础上，我设计了 ProSelect 的核心 Hook——useSelect，整体有 1000 多行代码，做了关注点分离：

顶层是 useSelect 作为编排层，下面拆分了 5 个子 Hook：useKeyboard 处理全键盘导航、useRemoteSearch 处理防抖搜索加竞态取消、usePagination 处理瀑布流触底加载、useSelection 管理单选多选状态和 Tag、useVirtualScroll 复用虚拟滚动能力。

最难的部分是状态协调——举个例子：用户输入了一个搜索关键词，远程搜索返回新数据后，分页要重置到第一页、虚拟滚动的行高缓存要全部清空、键盘导航的 activeIndex 要归零。这些操作如果处理不好顺序，就会出现各种诡异 Bug。

我的方案是引入一个事件驱动的状态机：每次数据源变更都会发出一个 reset 事件，各个子 Hook 各自监听这个事件来做清理工作，互不干扰。

最终成果： 10 万以上数据流畅渲染，FPS 稳定在 55-60。业务侧只需传入 columns、api、valueKey 三个核心配置，所有复杂交互开箱即用。原来开发一个企业级选择器要 2 天，现在 30 分钟搞定。

难点 5：JSON Schema 动态表单引擎与联动状态管理（约 1.5 分钟） ​

问题： 中后台系统里有大量表单，而且表单之间存在复杂的联动关系——比如选了「类型A」，下面要显示 3 个字段；选了「类型B」，要隐藏某些字段并且把另一个字段改为必填。传统写法全是 v-if 加 watch，一个 20 字段的表单能写出 400 多行模板代码，极其难维护。

我设计的方案分为两层：

第一层是 JSON Schema 配置化渲染——业务开发者只写一个配置数组，定义每个字段的名称、类型、校验规则和联动关系，组件库负责根据配置自动渲染成对应的表单 UI。

第二层是核心难点——formStore 状态管理器。 它专门处理字段间的 6 种联动关系：显隐联动、必填联动、禁用联动、选项联动（A 的值决定 B 的下拉选项）、值联动（A 变化时重置 B 的值）、以及校验规则联动。

技术实现上有两个关键难点：

第一是循环依赖检测。联动关系本质上是一个有向图，如果配置不当可能产生循环（A 影响 B、B 影响 C、C 又影响 A），会导致死循环。我在表单初始化时用 Kahn 算法做拓扑排序，一旦检测到环就在控制台报错并给出具体的环路径，帮助业务开发者快速定位配置错误。

第二是批量更新调度。一次字段变更可能连锁触发多个联动（visible 变了 → required 变了 → validate 变了），如果每次都立即更新 DOM 会导致多次重渲染。我用 Vue 3 的 watchEffect 配合 queueMicrotask 做批量收集，类似 Vue 的 nextTick 机制，把一个 tick 内的所有联动变更合并为一次 DOM 更新。

成果： 同样是 20 个字段的复杂联动表单，从 400 多行手写模板缩减为 50 行 Schema 配置，开发效率提升 70%，而且 Schema 配置是纯数据，可以存数据库做动态表单配置。

难点 6：多格式构建与双环境兼容（约 0.5 分钟） ​

工程化方面也有一些值得提的：

构建层面，组件库同时输出 UMD、ESM、CJS 三种格式加上 .d.ts 类型声明。难点在于组件库大量使用了泛型和条件类型，类型声明的自动提取经常出问题，最终通过 vue-tsc + rollup-plugin-dts 的组合方案解决。

环境兼容方面，因为我们的系统同时需要跑在浏览器和 Electron 桌面端，像 IntersectionObserver、clipboard 这些浏览器专属 API 在 Electron 中不一定完整支持，所以做了统一的环境嗅探和降级处理。

质量保障方面，Vitest 覆盖核心逻辑的单元测试、Storybook 8 搭建交互式文档、ESLint + Prettier + Husky + lint-staged 构成提交前的质量卡点，形成完整闭环。

总结收尾（约 1 分钟） ​

总结一下，回顾这两个项目，我的核心能力可以概括为三个层次：

第一是架构设计能力——在医疗平台体现为微前端通信架构的设计和模块联邦的依赖治理；在组件库体现为 JSON Schema 引擎的分层设计和 Hook 的组合式抽象。

第二是性能优化能力——医疗平台做到了首屏 40% 提速和 Rsbuild 迁移 60% 的构建加速；组件库实现了 10 万级数据的虚拟滚动流畅渲染。

第三是工程化能力——从 CI/CD 打包提速、模块联邦共享，到三格式产物构建、类型安全体系、完整的质量卡点。

一个项目锻炼了我在复杂业务系统中解决架构问题的能力，另一个锻炼了我沉淀通用能力、赋能团队的基建思维。我一直认为，做好一个组件库本质上不只是写代码，而是在用技术手段解决团队效率问题。两者结合，让我能站在更全局的视角去思考前端技术如何真正服务于业务价值。

以上就是我的介绍，感谢您的时间。
